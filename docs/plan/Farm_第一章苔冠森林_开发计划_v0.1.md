## 1. 开发目标与范围

以现有 Godot 4.6 农场、路线选点、卡牌战斗、格子背包和合作探索为基础，完成森林第一章的可玩版本。**先用可识别的占位背景、敌人、搜索物、图标和特效，把玩法、数据与同步做完整，再逐项替换图片。**

本计划中的“场景”采用现有路线节点上的主题探索场景：玩家选路，进入一个地点，点击搜索对象或开始战斗，搜刮后继续或撤离。五区各有独立背景、布局和物资池，共用交互模板。自由行走、无缝大地图和实时战斗不作为本轮的默认实现范围。

### 2.1 参考与采用的判断

- [Backpack Hero 开发者页面](https://thejaspel.itch.io/backpack-hero)将收集物品、整理背包与战斗组合在一起。本项目优先验证“搜索实体→装包→下一场来源牌变化”，具体卡牌与撤离规则来自本项目设计。
- [Godot 4.6 Resources 文档](https://docs.godotengine.org/en/4.6/tutorials/scripting/resources.html)区分场景节点与资源数据，并介绍资源复用。本轮据此分开玩法 ID 与表现资源；现有 Dictionary 定义继续沿用，不为森林单独迁移整个项目的数据格式。
- [Godot 4.6 随机数文档](https://docs.godotengine.org/en/4.6/classes/class_randomnumbergenerator.html)说明种子和状态的恢复，也提醒不要依赖底层算法长期不变。本轮保存已生成地图和战利品，不把“同一个种子以后再算一次”当作恢复方案。

## 3. 占位资源方案

占位的是美术表现，物品实例、卡牌效果、搜索进度、失败回滚和联机裁定均按正式玩法工作。

| 对象 | 首版占位表现 | 必须保留的辨识信息 | 后续替换方式 |
| --- | --- | --- | --- |
| 区域背景 | 原生几何/色块、远景轮廓、区域名 | 古道树木、神殿石柱、废塔层檐、营地木架、湿地浅水 | 背景资源 ID 换成图片或场景资源 |
| 搜索对象 | 简化图形＋名称标签＋点击高亮 | 树洞、马车箱、鸟巢、蜂巢、棺椁等轮廓不同 | 物体图替换，交互按钮与来源 ID 保留 |
| 敌人 | 简化身体＋武器轮廓＋名称 | 弓、盾、矛；三色史莱姆兼有元素图标 | 敌人图、倒地图和动作替换 |
| 物品图标 | 类别底板＋简化剪影；详情显示名称 | 实际占格、品质、补给次数 | 每个物品资源 ID 替换图标 |
| 卡牌 | 复用现有牌框，插画区放来源图 | 费用、目标、效果、来源与消耗提示 | 单独替换插画，不把文字烘焙进图 |
| 状态特效 | 火花、雪花、毒点、数字与日志 | 状态名、强度、到期时点 | 特效与图标替换，事件裁定保持一致 |
| NPC | 头像剪影＋对话文本＋明确选项 | 身份、交易内容和代价 | 头像与立绘替换 |

建议区域基色：古道苔绿与暖黄、神殿灰石与树脂金、废塔灰紫与铜色、营地木褐与炉火橙、湿地蓝绿与荧菌色。保留现有品质色；元素不能只靠颜色区分。

资源 ID 示例：`bg.forest_ch1.trail`、`enemy.forest_green_slime`、`prop.trail_hollow_log`、`item.forest_green_gel`。玩法存档只记录定义/实例 ID，不保存图片文件路径。资源未就绪时画出对应占位，不让整张界面空白。

图片首批可以先做五区风格图、核心敌人和常用搜索物。风格图属于参考图，只有满足背景构图、透明通道或切图规范的独立资源才标为“可接入”。

### 4.2 局内数据扩展草案

```text
run:
  content_set: forest_ch1
  content_version: 1
  chapter_id: moss_crown
  route_template_id: ...
  selected_branch: ...
  map: 已生成的完整节点与 edges
  resolved[node_key]:
    corpses: [...]                 # 已有尸体结构保留
    environment_sources: [...]
    selected_encounter: ...
    battle_won: bool
    search_gate: safe/guarded/resolved
    event_result: ...              # 已选择的事件结果
  chapter_pending[member_key]:
    clue_ids: [...]
    discovered_areas: [...]
    defeated_bosses: [...]

environment_source:
  id: 节点内唯一来源 ID
  template_id: trail_hollow_log 等
  kind: environment
  name: 玩家可读名称
  art_id: 表现引用
  regions: 与尸体区域相同的格子、items、searched 结构
  access: searchable/guarded/cleared
```

局内来源身份使用 `run_id + node_key + source_id + region_id`；物品仍使用既有全局发号规则。不同地点中同名的箱子拥有不同来源 ID；不能以显示名称或物品定义 ID 领取。

环境来源在首次进入节点时固定，包括物品实例、品质、次数、布局和守卫遭遇；战斗来源也必须与同一次生成的敌人配装关联。查看预览、搜索完成、关闭面板和重连均不重掷。

### 4.3 搜索操作与可见投影

保留已有 `search_start/search_step/search_cancel` 动作结构，通过来源查找同时支持 `corpses` 和 `environment_sources`。新增通用 `claim_source` 动作；旧 `claim_corpse` 兼容转发，避免破坏现有尸体流程。

UI 只提交来源、区域、实例和目标位置；权威端验证当前节点、搜索门槛、已揭晓、未领取、归属与布局。成功装包后再标记已取走；失败不改变来源。同一次请求重放必须返回同一裁定结果。

可见投影必须过滤两类来源。未揭晓时仅显示中性占格轮廓；隐藏定义、实例 ID、品质、价格和牌效不得从首次快照、重连快照、动作回执或提示中提前得到。现有搜索计时与品质展示节奏先复用，新增时长另作试玩参数，不在本计划重新宣布旧时长。

### 4.4 路线方案与节点身份

森林采用一张约 12 排的完整路线，前半段古道，后半段为本局选择的目标区域。保留现有 `r行c列` 节点键，整张图内不重复行号；跨区不清空 `resolved`。

| 排数 | 内容 |
| --- | --- |
| 0 | 古道入口、装备检查 |
| 1～3 | 古道战斗、搜索、事件；头狼作为可避开的高风险候选 |
| 4 | 休整/撤离点 |
| 5 | 四条区域入口：神殿、废塔、营地、湿地 |
| 6～8 | 目标区域的搜索、战斗、事件 |
| 9 | 深入前休整/撤离点 |
| 10 | 区域强敌；未开放神殿深处时改为外殿收尾节点 |
| 11 | 区域出口、撤离结算 |

路线保存显式 `edges`。选中某支路后不能横跳到另一支路；本次不实现中途横穿营地与湿地的额外路径，地理联系先用背景和事件说明表现。地图绘线、按钮禁用、单人移动和双人投票都读取同一合法边集合。

当前源码的 `GATE_ROW=8`、下一层切换和路线固定 `/9` 布局需要为森林改为内容集数据；旧洞窟继续按原层数规则运行。森林的区域强敌胜利后先搜刮，再走出口，不误触发进入铁根矿窟。

### 4.5 保存、旧档与个人进度

- 当前农场保存版本为 7、局档主要格式为 1。森林新增字段优先采用可缺省的扩展，不机械升全局版本；若实际序列化需要升版，先补迁移表和夹具，再变更版本。
- 缺少 `content_set` 的旧局按旧洞窟恢复，已裁定奖励与尸体原样保留；禁止把进行中的旧局转换为森林或补发森林物资。
- 新局保存 `content_version`、地图、已裁定来源和战斗行为计数。版本不支持时明确阻止加载并保留原档，不静默重建。
- 个人新增 `expedition.chapters.moss_crown`，保存已发现区域、线索与首通。局内先记入 `chapter_pending`，在现有结算事务中按成员合并并幂等去重。
- 初值：知识类线索即使探险失败也可记录；种子、材料与制作解锁仍以实际成功带回或保险箱保护为准。此规则仅决定新章节的知识进度，不扩大物品保护范围。
- 神殿深处初值需要两条不同的教团线索；线索至少来自两个可选来源类别，并保证常规探索有确定来源，避免纯随机卡住。其他三区不作为必须通关的钥匙。
- 双人出发时按成员已持久化线索的并集判断本局神殿深处是否开放，快照明确告知。新线索可更新本局条件；离队不撤销本局已确认的入口条件。每人的发现与首通分别结算。

## 5. 工作阶段与验收

阶段状态均为待实施。每阶段完成后记录实际文件、采用初值、验证结果和偏差；不把后续阶段的测试写成已经通过。

### P0：内容登记、占位规范与兼容准备

依赖：无。

- 按附录 A 登记 36 个物品映射、23 个敌人、43 类搜索对象、区域与卡牌 ID；复用现有定义，不创建同名重复铜短剑或铜片。
- 建立 `ChapterOneDefs`、资源查找与占位规范，五区可以通过开发预览入口显示名称、背景和代表搜索物。
- 确认探索场景为现有卡牌路线内的点击场景；资源替换不改变命中区和玩法 ID。
- 为旧农场、旧单人局、旧双人局、新森林局准备隔离测试夹具；记录当前代码基线，保留原可玩入口。
- 定义内容开关与版本检查，在主机和专用服务端的出发构造链路预留内容集参数。

验收：所有设计编号都有稳定映射；五区占位可识别；缺图有回退；旧局仍能按原内容加载。

### P1：物品、卡牌与元素效果

依赖：P0。

- 在 `ItemDefs/CardDefs` 中完成全部物品与牌定义。16 个新增牌型中，射击、突刺、强射、敲击、守护铃、烟幕复用现有伤害/格挡模板；其余按内容设计接入。
- 完成灼烧、寒冷、净化、部分忽略格挡，并同步卡牌短文案、完整说明、图标、伤害预览和战斗日志。
- 灼烧在受影响单位下一次行动开始结算一次并清除，取最高强度、不叠加；与现有中毒时点分别实现，避免顺手改动旧中毒规则。
- 寒冷只减受影响行动阶段第一段攻击 2 点，最低 0；多段攻击只减第一段，即使第一段被格挡也消耗效果。不攻击也在该行动结束时清除，重复施加不累加。
- 伤害计算顺序初值为基础伤害→既有易伤/虚弱与取整→寒冷减值→部分穿透→格挡→生命；预览与实际共用计算入口。
- 微光弹的“忽略至多 3 格挡”：目标有 6 格挡、受到 5 点微光伤害时，实际抵消 3 点、损失 2 生命，剩余 3 格挡。不能顺便把忽略的格挡也删掉。
- 一次性来源共享剩余次数；2 格绳网的投网牌与负担牌属于同一实体，投网消耗后连同尚未洗入的关联牌一起移除。
- 给装备确定类别：盾沿用现有防具兼容方案；短剑、弓、矛、弩、铃杖、符杖属于武器；护甲/披肩为防具；羽饰、号角、火把、提灯使用容器，不新增饰品槽。

验收：36 件物品逐件满足面积=牌数；27 个牌型均能解释并执行；补给无重复使用；同一计算在单人、双人与序列化恢复后结果一致。

### P2：首批敌人与固定战利品

依赖：P1。

- 首批完成 9 种常规敌人：弓手、剑盾哥布林，三色史莱姆，森林狼、穴蝠、裹尸守卫、封棺祭司；以及头狼、根棺祭司两个强敌。
- 扩展敌人意图的有限自愈、治疗同伴、保护同伴和蓄势空档；目标和次数在意图生成时确定，文本显示目标与剩余次数。
- 剑盾兵给同伴的防护必须覆盖接下来的玩家阶段。现有敌人各自行动前清格挡，直接加给排在后面的敌人会立即被清掉；本轮把这类护佑记录为阶段末统一生效的授予列表，并校验目标仍存活，避免敌人排列顺序改变防护结果。
- 治疗次数、已用补给与行为阶段进入战斗快照。满血时的替代动作在意图确定时决定；恢复战斗不刷新次数或隐藏换招。
- 遭遇一次生成敌人配装与固定掉落：显示持弓的敌人对应短弓来源；材料按身份分配，不继续把旧通用奖励轮流塞进无关尸体。
- 整场控制总收益预算，装备价值计入预算；固定护卫不额外复制整场奖励，不加入无限召唤和分裂刷取。
- 根棺祭司先采用明确循环与普通数值；“火压制一次修复”列为 P6 的附加交互，普通物理配装始终有通关路线。

验收：9＋2 敌人可单独开战；三色史莱姆战术不同；治疗有限；护佑不受敌人排序影响；看见的装备与可搜来源一致。

### P3：环境搜索、守卫事件与场景交互

依赖：P0、P1；守卫战验证依赖 P2。

- 先对现有尸体搜索做行为保持的抽取，再加入环境来源工厂；旧尸体装备槽、野兽遗骸、租约和投影继续工作。
- 用树洞、马车箱、蜂巢、棺椁四类样例跑通“进场景→点对象→逐件揭晓→拖入背包/装备→关闭回到场景”。
- 每个节点初值展示 2～4 个对象，具体模板从所属区域的候选集中生成；43 类是模板总数，不是一张场景同时放 43 个可点击物。
- 显示未搜索、搜索中、尚有物品、已搜空状态；点击区域优先保证名称、高亮与鼠标命中一致。
- 蜂巢、活动石棺等带风险的对象先展示迹象与处理选项。选择挑战后保存固定遭遇并锁住来源；胜利后开放，不重复生成奖励。可绕过的风险物不阻塞普通离开。
- 装包失败、布局取消、关闭重开、切换来源、保存恢复均保留已裁定内容。多格物品整体揭晓，同类物品按实例分别领取。
- 离开检查两类来源的未取物品和其他成员搜索状态；确认离开后不允许返回旧节点重领。

验收：四类样例都能完成搜索与装包；未揭晓不能领取；无重开刷物资；守卫战胜负正确控制来源；原尸体搜刮回归通过。

### P4：森林路线、入口与章节日志

依赖：P2、P3。

- 实现第 4.4 节的路线模板与显式边集合，森林节点带 `area_id`；区域名、背景、敌人池、物资池随节点一起确定。
- 增加森林开发入口；本地单人、合作主机、线上服务端统一通过内容集构造入口，不只改本地硬编码 `moss_stone_shallow`。
- 扩展节点预览，预览只读，不提前生成/消耗节点随机或改日志。风险、区域与公开敌人信息可看，未知物资详情保持隐藏。
- 接入日志中的教团线索、区域发现与首通条件。日志按钮读状态；发现事务只触发一次，不由“打开日志”触发奖励。
- 森林首领和出口使用内容集规则，路线高度与连线按实际排数计算，避免固定 9 排导致底部按钮错位。
- 在节点切换、跨区、撤离和死亡处保存；断线恢复回到原节点与原来源状态，不重新选择支路。

验收：古道可通向四个区域；支路不能横跳；两处提前撤离可用；神殿外殿与深处条件可解释；森林不进入旧矿窟下一层。

### P5：古道＋神殿的可玩样例

依赖：P0～P4。

- 将古道 10 类、神殿 9 类搜索模板接入区域池；每局按池生成，不要求一局出现全部。
- 完成两区占位背景与对象布局，鸟巢、蜂巢、旅人行囊、石棺、蓄水池等都有独立点击表现。
- 至少安排三条可复现样例：蜂蜜用掉或带回；蓝凝胶下一战减攻；拿古银器后带负担继续或撤离。
- 首领入口未开放时仍可搜外殿并安全收尾；开放后能挑战根棺祭司、搜刮、走出口并记录章节目标。
- 真实窗口核对 1280×800 与 1024×640：对象、牌区、搜索格、详情和退出按钮不互相遮挡。

验收：真实输入能完成“备战→古道→神殿→搜索/换装→下一战→撤离→查看仓库”；所有画面可用占位资源完成，不能依赖尚未生成的图片。

### P6：其余三区、敌人扩充与农场反馈

依赖：P5。

- 加入废塔、营地、湿地各 8 类搜索物，共补齐 24 类，完整章达到 43 类。
- 补齐另外 9 种常规敌人和 3 个区域强敌，完整章达到 18＋5。至少配置每区的入门、普通、强敌遭遇，跨区复用史莱姆时不另造能力变种。
- 所有搜索池按地点检查来源：鸟巢不出武器，冷泉不出红凝胶；祭火石龛可出现红史莱姆，活动尸体不直接掉干净敷料。
- 银叶草、萤菇接入现有种植、生长、仓库、首次带回/收获解锁、种子购买、育种与市场路径；生长模型先用现有植物阶段占位，并清楚显示新名称。
- 增加 7 条配方关联：绿凝胶＋银叶草→小药水；麻布＋银叶草→绷带；树脂＋纤维→树脂护甲；树脂＋纤维→火把；纤维→绳网；蝠翼＋麻布→披肩；萤菇作物→腐菌囊。具体数量、金币和解锁初值在实施登记表集中配置并试玩调整。
- 材料与种子仅以实际结算结果解锁；没有带回的未领取战利品不计数。新种子可保护，其他物品不因为“体积小”自动进入保险白名单。
- 五类非敌对角色先实现为事件头像与文本选项：药师提供制剂知识，猎人给狼踪，货郎交易，伐木工给营地线索，中立哥布林以铜片换蜂蜜。交易在权威端验证材料与容量，连点/重试只成交一次。
- 本轮收藏以已有仓库存留和出售为基础；木雕、银器和铜环显示收藏用途标签。农场自由摆放、完整家具编辑器单独列为后续扩展，不在本轮隐含新增。
- 如加入火抑制修复，限定到明确敌人标记，写出意图说明，并验证不带火仍可击败；不建立全游戏隐藏元素克制表。

验收：五区均有可完成路线；23 敌人、36 物品、43 搜索模板能追溯来源；两种植物与七条配方闭环；NPC 事件无复制收益。

### P7：合作、保存与异常恢复集中验收

依赖：P6；相关权威入口应在此前各阶段同步实现，不到本阶段才补第二套逻辑。

- 本地会话与线上服务端同时支持环境搜索、通用领取、区域选路、守卫事件、日志和章节结算。
- 两人可搜索不同来源；同一区域占用复用既有租约。两人领取同一实例只有一次成功，满包失败不抢走归属。
- 共享发现与个人领取分开：揭晓结果全队可见，物品领取后归领取者，来源全队只一份；知识进度按当场有效参与成员记录，物资按各人携带结算。
- 合作推进、守卫事件与撤离沿用团队裁定，不能由一名玩家点搜索物就悄悄让另一人丢掉未处理物资。
- 同一局在普通节点、搜索中、战斗中、领取后、首领战后与结算回执重试时分别恢复；中断的搜索释放旧运行期租约，已揭晓和已领取不回滚。
- 出发握手检查森林内容与规则兼容性。旧客户端不支持新效果时明确拒绝进入新局，已进行旧局不强制迁移。
- 所有新结算字段进入既有事务和去重路径；专用服务端保存失败时不先回成功再补写。

验收：本地单人、本地双人、专用服务端双人三条路径结果一致；恢复不复制、不吞物品、不刷治疗次数；旧档资产保留。

### P8：数值、表现替换与交付

依赖：P7。

- 按实际试玩检查普通战斗轮数、补给消耗、货物负担、区域收益、首领难度与两种作物供给。记录初值和调整原因，不以本次设计稿数值宣称平衡完成。

- 检查设置中的减少动态/特效、快速表现、音量等兼容行为。音效先复用现有类别，新增音色可后换。
- 完整章走查：五区、首领、NPC、日志、农场、制作、出售、双人分享、死亡与撤离。
- 输出实施报告、实际内容清单、已知限制、截图与测试结果，更新文档入口与试玩说明。

验收：完成第 6 节矩阵；可区分“占位可玩完成”与“正式美术已替换”；公网真人双机未做时单独保留待验状态，不用本地测试替代。
