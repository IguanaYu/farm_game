**证据边界**：地址簿、线上房间及线上局使用演示条目／内存镜像，未连接真实服务器，不能据此宣称公网或真人合作验收通过。拜访场景使用本地构造的主人和真实农场状态结构，直接调用现有入口复现视图问题；这验证的是客户端场景路径。小窗口截图反映当前整体缩放，1024×640 时逻辑视口仍为 1440×900；未把控件的逻辑最小尺寸直接当作物理越界证据。

## 2. 整体判断

当前项目存在两种完成度：规则、资产和部分卡牌／搜刮交互已经较完整；空间表现、场景交互和跨模块一致性仍处于占位阶段。

农场扩大了地面，商店、营地与好友家也有节点和入口，但参考稿中的构图、环境层、生活物件、人物对白、对象工作区没有系统落地。农场 UI、旧战备／制作 UI、新矿洞 UI、线上简化 UI 又各自使用不同布局。结果是每个功能可以单独打开，整体却不像同一个世界。

[R3 实施计划](../plan/Godot_合并路线_R3_农场环境与商店内景_代码执行计划_v0.1.md)明确把真实镜头、光照和视觉验收列为非目标；人物气泡与分步交易也推迟。[R5 打磨计划](../plan/Godot_合并路线_R5_M4异常运维与打磨_代码执行计划_v0.1.md)主要补了结构、音乐和轻微动作。现有结构回归通过，不代表这些参考画面已经复现。后续必须分别记录“功能通过”“视觉通过”“实际操作通过”。

参考稿是 HTML/SVG 交互示意，不是可直接导入的完整 3D 场景。需要将镜头、模型比例、材质、光照和投影界面落实到 Godot；构图、人物可见性、物体入口和操作流程仍应对齐。

### 优先级

| 优先级 | 含义 |
| --- | --- |
| P0 | 已复现的客户端路径阻断，应先修 |
| P1 | 主要设计缺失、明显画面问题或关键操作不一致，属于这一轮对齐范围 |
| P2 | 基础对齐后完善的细节、反馈、组织和验收工具 |

清单中“补齐”指设计稿已要求但当前缺失；“修复”指当前实现有问题；“增强”指体验完善。不是把全部功能重新开发一遍。

## 12. 建议落地顺序与验收出口

这是一份改动清单，不代表已经开始修改游戏。建议按下面的依赖分批落实，避免各地点独立做完后再次出现风格和交互差异。

| 批次 | 范围 | 这一批必须看得见的结果 |
| --- | --- | --- |
| 1 | B-01～B-05；Q-01／Q-03 的最小检查基准 | 好友家完整真实点击往返，农场恢复；ESC 只关闭当前界面；当前基准画面和缺陷证据固定 |
| 2 | G 类规则与风格；F 类农场 | 一个完整、连续、可操作的农庄；入口可认，普通田地操作不盖住整个世界；三个桌面尺寸可读 |
| 3 | S 类商店；U-01／U-02 工坊 | 大客人、对白、报价、作物篮和货架成为实际操作主体；买卖与工坊流程完成后仍留在地点 |
| 4 | C 类营地；U-03 配装；X-01／X-04／X-09 | 队友与准备状态可见；线上和离线共用路线／预览／结算展示；营地接住完整出发和撤离 |
| 5 | X 类其余洞内表现；V 类好友家；U-04～U-06 | 三层洞窟可辨，战斗／搜刮连续；好友家有主人身份与生活感；登录／工作区一致且可读 |
| 6 | P2 表现与维护项 | 轻微动作、反馈、声画衔接和资源维护完善；既有规则／线上权威／资产隔离继续成立 |

视觉修改以真实 Godot 运行画面评审；HTML 预览继续作为构图与交互依据。每一批先拍真实目标画面再接操作，避免先完成节点数量、最后把全部视觉工作留给用户判断。

### 最低验收矩阵

- 画面：1440×900、1280×800、1024×640；记录 PNG 的物理尺寸与逻辑视口，正文／报价／按钮保持可读。额外窄窗口只用于发现风险，移动端仍不自动纳入支持范围。
- 农场：空地、生长、成熟、待扩地、仓库满、育种模板有／无；入口及弹出区互不遮挡。
- 商店：不同批次、数量、同价最高、售罄、兜底整批、锁客人／锁公式、每日刷新；展示准确，成交保持原有数量语义。
- 地点：农场→商店→农场；农场→营地→配装／组队→营地；地址簿→指定院子→指定小屋→院子→自家。各路径十次往返仍正确。
- 探险：线上／离线、p1／p2 视角、节点预览／投票、战斗、奖励／搜刮、休整／出口、结算；失去连接与等待队友时状态可读。
- 拜访：在线／离线／未开放／读取失败；同一 owner_id 贯穿院子、小屋、作物与留言；访问他人时不产生他人资产写操作。
- UI：ESC、关闭、返回、切换对象、鼠标真实拾取、键盘聚焦；正常工作区与危险确认分开，提交处理中不重复执行。

保留现有规则回归，按实际修改范围运行相关检查；涉及客户端适配时再做权威快照与公网复验。没有改动服务器和规则的纯美术工作，不应顺带扩展经济／战斗玩法。
