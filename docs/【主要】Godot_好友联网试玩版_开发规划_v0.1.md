# 【主要】小小农场：好友联网试玩版开发规划 v0.1

编写日期：2026-10-02。状态：**推荐规划，尚未实施、尚未完成联网验收**；§10 关键范围决策已于同日与用户逐项确认，见 §10 决策记录。

目标：让开发者和受邀朋友在各自网络下，连续试玩“经营个人农场 → 配装 → 单人或双人下洞 → 带回资源 → 制作与成长”，可以隔天回来接着玩，并能定位试玩中出现的问题。

本规划补充现有第二大阶段计划，集中处理好友互联网试玩所需的联网、存档和交付功能；不把现有本机回归结果当成公网交付完成，也不重复安排已经实现的玩法内容。

## 0. 规划前提与当前证据

### 0.1 推荐的首版范围

| 项目 | 本规划的推荐基线 | 确认状态 |
| --- | --- | --- |
| 发行方式 | 小范围邀请试玩，先交付 Windows 客户端 | 推荐；现有导出目标为 Windows Desktop |
| 农场 | 各人自己的农场；操作需要联网，退出期间仍继续成长 | **已确认（2026-10-02）：断网不能播种/收获/买卖，服务器为唯一权威资产** |
| 洞窟 | 沿用现有单人和双人 PvE；每个合作房间最多两人 | 沿用现有玩法；朋友总人数与每局人数分开 |
| 服务器 | 统一保存线上农场资产，裁定洞窟，完成回家结算 | 推荐方案，实施前冻结；并非已经迁移 |
| 存档 | 新建独立线上试玩档；现有本地档保留，不自动上传或覆盖 | 推荐，避免旧档来源与初始资产影响试玩数据 |
| 试玩规模 | 建议先邀请 5～10 人；服务器允许同时存在多个房间 | 已确认（2026-10-02）：首批 6～10 人，全部 Windows；容量按 §7.1 T16 验证 |
| 观察周期 | 建议正式发包后试玩 7～14 天 | 观察建议，不是开发工期承诺 |

“第一个试玩版”指首个可持续游玩的联网版本，不等于前面讨论中的第一个网络方案。

如果农场必须保留完全离线操作，应在 M0 之前改写本规划：最省改动路线为本地农场＋房主裁定洞窟＋服务器中转。此路线继续采用好友信任下的本地资产，不能同时宣称服务器掌握权威农场资产。不要在实施中途悄悄混合两套存档归属。（2026-10-02 已确认采用联网基线，不触发本改写路线；留作记录。）

## 1. 玩家最终应该能怎样玩

1. 收到 Windows 试玩包和自己的邀请凭据，解压运行，无需安装 Godot。
2. 首次激活账户、填写昵称，得到新的线上农场；之后启动自动恢复同一账户。
3. 播种、浇水、收获、卖菜、育种、制作和配装，进度由服务器保存。
4. 关闭游戏；第二天回来，作物、育种机和每日市场按服务器时间计算。
5. 一个人按现有规则下洞，或创建双人房间，把房间码通过现有聊天工具告诉朋友。
6. 朋友输入房间码，双方准备、出发，各自正常出牌、选路、拾取、分享并撤离。
7. 回到各自农场，装备返还、药水消耗、获得物和损失全部正确入账。
8. 网络断开时看到清楚的状态；恢复网络或重启客户端后，继续自己的农场或同一局。
9. 出问题时可以复制错误编号、版本和局编号，导出诊断包，向开发者反馈。

首版的多人体验是“两人共同探险，各人经营自己的农场”。农场互访、共同种地和角色实时走动不是本轮交付承诺。

## 2. 网络与服务器分工

```text
Windows 客户端 A                  Windows 客户端 B / C / D ...
         └──────────────┬──────────────┘
                        ↓ 加密连接
                  公网游戏服务入口
                        ↓
               Godot 无界面游戏服务端
         ┌──────────────┼──────────────┐
      身份与会话     个人农场与资产    房间与洞窟局
         └──────────────┼──────────────┘
                    事务型存储
                        ↓
                  备份与运行记录
```

- **农场按操作处理。** 客户端请求播种、购买、出售等；服务器检查并保存，返回结果和新视图。作物成熟使用播种/到期时间，不给每块地建立持续运行的联网计时器。
- **卡牌按动作同步状态。** 服务器排序并处理出牌、领取、投票等，提交后发送该局快照及表现事件。首版优先使用完整快照，实测消息体大小后再决定是否需要增量。
- **客户端负责表现。** 倒计时、动画、音效、选牌预览、拖动预览可以本机完成；资产和战斗结果以服务器确认值为准。显示倒计时不代表已经获得收获资格。
- **同一台机器可承担这几项职责。** 首版不拆微服务、不一局占用一台机器；多个房间共享服务进程，各自有独立状态和请求队列。

### 2.1 连接与存储的推荐选型

1. 服务端继续使用 Godot 4.6 系列，独立无界面入口，复用 GDScript 规则。先验证目标服务器系统和架构；不启动农场 3D 场景、不依赖 GPU。
2. 公网传输首选 **WSS（加密 WebSocket）＋现有 JSON 消息思路**。我们的玩法消息频率低，优先保证公网接入、凭据加密和维护方便。Godot 的 `WebSocketMultiplayerPeer` 可作为传输适配层，不要求把所有规则改成场景树 RPC。
3. 入口选型已确认（2026-10-02）：不使用域名，客户端内置自签证书/CA，直连 `wss://服务器IP:端口`，TLS 由 Godot 服务端直接提供，不用反向代理；后续如升级域名需重发客户端包。M0 验证该端口在服务器防火墙/安全组放行、实际公网可达。
4. 现有 ENet 用于旧单机/局域网回归保留。若 M0 证明实际服务器环境更适合 ENet，需要明确加密、身份传递与端口方案后修订规划，不能直接把邀请凭据放进未加密的公网消息。
5. 持久存储首选单机 **SQLite**，账户状态、局快照、请求收据、结算记录在同一数据库内提交。M0 必须验证 Godot 适配依赖的许可、4.6 兼容性及目标平台导出；选型未通过前不把数据库接入记为已完成。
6. JSON 仍用于消息、诊断和测试样本。不能把现有多个 JSON 文件逐一保存，直接当成跨两名玩家的原子结算。

这两项选型是推荐，均需最小原型通过后冻结。完整快照的体积、WSS 排队及数据库提交耗时都要测量，不能仅凭“回合制”推断不存在瓶颈。

## 3. 首版必须实现的功能

“必做”表示进入连续好友试玩前必须通过对应验收。已有玩法主要做联网适配和验证，不能把所有内容都视为重写。

### 3.1 身份、登录和版本

| 编号 | 功能 | 完成条件 |
| --- | --- | --- |
| N01 | 邀请激活与固定玩家账户 | 开发者发放一次性邀请凭据；激活后绑定稳定账户，昵称只用于显示；未受邀者不能创建线上档 |
| N02 | 自动登录与人工恢复 | 本机保存可撤销的登录凭据；重启回到同一档；更换电脑或凭据丢失时开发者可重发恢复凭据，不靠昵称冒认 |
| N03 | 一账户单个活动会话 | 重复登录明确提示；切换到新连接时旧连接失效，避免两台电脑同时修改同一档；重连不能挤掉别人的账户 |
| N04 | 版本握手 | 区分客户端构建、网络协议、规则、数据库结构版本；不兼容时拒绝进入并说明应使用的包，不在局中才报错 |
| N05 | 基本请求保护 | 未登录请求、越权账户/房间、超大包、异常字段和频繁请求被限制；房间码不是账户凭据；日志不记录邀请/登录密钥 |

首版不做手机号、邮箱、社交登录和完整账号门户。身份功能需要简单，但不能以“客户端说自己是谁”替代认证。

### 3.2 农场和个人资产联网

| 编号 | 功能 | 完成条件 |
| --- | --- | --- |
| F01 | 线上新档、载入与保存状态 | 统一初始资源；客户端只缓存线上视图，服务器保存实际档；保存失败不能显示成功 |
| F02 | 播种、照料、收获 | 种子扣除、地块、时段浇水、施肥与收获由服务器执行；重复点击/重试不重复扣种子或发作物；批量操作逐项结果可见 |
| F03 | 仓库、育种与育种机 | 种子回收、模板设置、升级、复制和领取联网；退出期间的累计产出遵守原有容量与暂停规则 |
| F04 | 商店、扩地与升级 | 买种子/肥料、扩地、仓库、水壶、商店等现有资产变更全部走服务器，不能遗漏某个 UI 旁路 |
| F05 | 市场与出售 | 客人/公式及锁定操作由服务器确定；报价与成交重新校验；拆批、兜底、批量出售不重复入账 |
| F06 | 制作、目标与解锁 | 配方解锁、制作、设施/成长目标、奖励领取走同一资产入口；材料扣除与产出保存同时完成 |
| F07 | 装备仓库与战备 | 放置、旋转、整理、配装和弃置请求经过服务器；界面可预览，确认后才修改正式资产；占用中物品不可另作他用 |
| F08 | 服务器时间 | 播种、照料、生长、育种结算和北京时间每日刷新统一使用服务器时间；修改电脑时钟不影响线上收益 |
| F09 | 在线状态与本地档隔离 | 显示连接中/在线/重连/维护；断网后停止提交资产操作；不把缓存或旧本地档覆盖到服务器 |

所有改变资产的现有操作必须列入命令清单逐项对照，包含待领取区、批量动作和教程奖励。只联网播种和收获，而出售或制作仍本地保存，不能算 F01～F09 完成。

农场基础玩法沿用现有内容和数值。首版不额外扩地上限、加新品种或重做经济系统；试玩发现卡关，再按证据调整。

### 3.3 房间与单人/双人洞窟

| 编号 | 功能 | 完成条件 |
| --- | --- | --- |
| C01 | 创建、房间码加入、离开 | 输入短房间码即可加入，无需朋友配置路由器；处理错误/过期码、满员、已开局、已在其他局等情况 |
| C02 | 多房间隔离 | 不同朋友可同时开不同房间；任何快照、领取、分享和结算都只影响所属局；同时两人争最后名额也不能超员 |
| C03 | 成员、准备、取消准备与出发 | 显示昵称、在线状态、准备状态；修改战备撤回准备；双方准备后由房间创建者发起，服务器重新检查并开局 |
| C04 | 房间创建者和服务器分离 | 创建者只是有发起权限的玩家；等待房间中其离开可交接权限；开局后任何人的客户端都不是游戏服务端 |
| C05 | 保留单人探险 | 单人也通过服务器运行现有规则、保存进度和结算，避免单人与合作形成两套线上资产来源 |
| C06 | 双端独立卡牌操作 | 双方自己选牌、目标、结束回合、使用消耗品和救援；合法性与顺序在服务器处理；不依靠创建者代操作 |
| C07 | 选路、事件、休整、搜刮与分配 | 完整接入现有节点、共同投票、背包与公共物资规则；同时领取同一物只能成功一次；满包拒绝不吞奖励 |
| C08 | 分享、撤离、死亡与放弃 | 现有分享确认/取消、共同撤离、死亡保护、个人放弃完整可用；退出程序与断线不自动等同死亡或撤离 |
| C09 | 快照与信息范围 | 加入/重连拿当前局快照；操作确认后收到新状态；只发送该阶段允许玩家知道的信息，不提前泄露未揭示奖励或随机结果 |
| C10 | 合作沟通 | 复用已有快捷信号并验证双端可见；语音/长文本聊天由朋友自己的聊天工具承担 |

合作人数继续是两人。支持十名测试者并不意味着要立刻把一局改成十人，新增三至四人会影响牌组、敌人和共同回合规则，另列后续阶段。

### 3.4 出发、回家与恢复

| 编号 | 功能 | 完成条件 |
| --- | --- | --- |
| S01 | 统一带入检查和占用 | 从服务器资产读取携带物和牌组；一次事务建立局与双方占用；任一检查/保存失败，两人都不开局，已有资产不被扣走 |
| S02 | 动作去重与过期保护 | 相同请求重试返回原结果；同一编号不同内容拒绝；落后状态不能覆盖新状态，返回重同步信息 |
| S03 | 消耗、获得、转移与结算 | 按实例逐件记账；一次事务保存需要一起生效的双方资产、局状态和结算收据；带入装备不额外再发一份 |
| S04 | 未送达结果查询 | 服务器提交后消息丢失，重连/重试可以查询原结果；客户端“看到了结算”只是送达确认，不触发第二次入账 |
| S05 | 自动重连与重新进局 | 恢复同一账户、同一局、同一已提交状态；不会重新抽图、重抽奖励或新建一局；有明确手动重试入口 |
| S06 | 队友掉线与暂停 | 沿用合作局暂停等待的方向；建议自动重连窗口先沿用 120 秒配置。超过窗口提供重试/稍后恢复/明确放弃入口，不因超时自动判死 |
| S07 | 客户端关闭与服务端重启 | 客户端重启能恢复；服务端恢复已提交的农场、局、随机进度、占用和未查看结算；恢复后重新认证并暂停待成员返回 |
| S08 | 满仓、失败与中断提示 | 满仓按原待领取区接收；磁盘满或数据库失败拒绝变更并保留已提交状态；不能先广播成功再发现未保存 |

长期无人在线的局可以从内存移出并保存，避免一直占用活跃房间资源；持久局和占用不得静默删除。玩家重新上线可恢复，或者按明确展示的放弃规则结束。首版不设置未经确认的自动清档/自动惩罚期限。

个人放弃后队友能否继续、双方共同撤离与失败规则，继续遵守现有规则。新架构要验证它们，不能因为服务器在运行就绕过“队友掉线暂停”。

### 3.5 交付、运维与反馈

| 编号 | 功能 | 完成条件 |
| --- | --- | --- |
| O01 | 独立服务端导出与配置 | 启动后无需打开桌面；地址、端口、存储目录、人数限制和环境配置明确；开发与试玩数据隔离 |
| O02 | 进程维护与状态检查 | 系统适用的守护方式支持启动、重启和异常退出后恢复；提供只读健康状态、在线数/房间数/错误计数 |
| O03 | 备份与实际恢复 | 运行中生成一致备份，保留最近七天与更新前备份；至少在隔离环境恢复一次。原盘损坏仍可从另一位置找回备份 |
| O04 | 维护和版本更新 | 能关闭新局入口、提示维护并保存现有局；更新前备份，重启后恢复。客户端版本错误时能清楚知道应下载哪个包 |
| O05 | Windows 试玩包 | 解压即运行，连接地址预配置；有构建号、更新说明、玩家指引，调试发物和时间快进关闭 |
| O06 | 诊断和试玩记录 | 显示可复制的问题编号；诊断含构建、错误、账户内部编号、房间/局/动作编号和时间，排除凭据；可以手动导出反馈包 |
| O07 | 最小管理入口 | 通过受限命令/配置发邀请、撤销或重发凭据、查看未决局、查结算、触发备份和维护；不必开发后台网站 |

自动更新器不属于首版必做。首版手动下载替换包即可，但必须保留客户端凭据/设置，并能检测不兼容版本。

## 4. 资产和持久化的实现约束

### 4.1 线上状态的唯一来源

- 服务端保存个人农场、装备、材料、进度与教程状态；客户端缓存可以丢弃后重新拉取。
- 请求里的账户身份来自已认证连接，不来自客户端自报字段。客户端仅提交目标物品/地块和操作参数，不提交新金币数、攻击结果或整份资产覆盖。
- 局内与农场里的同一物品不能同时可用；装备在出发时占用，携带副本用于局中规则，回家结算解除或完成转移。
- 农场各人的种子/作物批次可以继续按账户内编号管理。跨玩家分享的装备实例必须在服务端有唯一编号和归属；推荐给线上装备使用服务端统一 `id_pool`，保留规则层 `instance_id: int` 字段。
- 旧离线 ID 格式和存档不强行改写。线上分配器、账户映射与请求编号在服务层声明；数字 JSON 往返要保留已有归一化处理，编号上限和精度在 M0 验证。

### 4.2 每次变更先保存，再回复成功

服务端建议统一走下面的入口：

```text
认证/房间权限 → 查请求收据 → 检查状态版本 → 调用现有规则
    → 保存新状态＋收据（同一事务） → 发布结果和快照
```

需要持久化的最小记录：

| 记录 | 必要内容 |
| --- | --- |
| 账户/身份 | 稳定账户编号、昵称、邀请使用记录、可撤销凭据的校验信息 |
| 个人档 | 农场/资产状态、结构版本、状态序号、活动局引用 |
| 洞窟局 | 成员账户映射、局状态、状态序号、随机进度、暂停状态 |
| 请求收据 | 账户、稳定请求编号、操作内容校验、结果、关联状态版本 |
| 结算 | 唯一结算编号、局、各人的带入/获得/消耗/损失、已应用标记 |

规则处理应在受控状态副本上进行；提交失败时丢弃候选副本，避免内存显示已变更而磁盘仍是旧值。跨玩家分享、出发和共同结算必须协调受影响账户与局的执行顺序，不只对某一连接排队。

重试使用同一稳定请求编号；重新登录不能清空去重记录。首次开局确定的地图/奖励和随机过程需可恢复，不能靠客户端重连重新生成。首版可以保留试玩期间的收据，清理策略留待实测后制定。

### 4.3 两类恢复必须区别

- **进程退出/重启：**恢复到最后成功提交的状态；已返回成功的操作不应因进程重启丢失。
- **磁盘或整机损坏：**只能恢复到可用备份时点。已确认（2026-10-02）采用本地/手动备份：每日至少手动下载一次一致备份，每次更新前额外备份。因此整盘损坏的回退窗口为“上次手动备份”，可能达数小时至一天，不能按 30 分钟窗口宣传；进程重启恢复（上一条）不受此影响。若试玩中回退窗口不可接受，再升级为对象存储自动上传。

备份用数据库一致备份机制或经过验证的停写流程，不能随手复制正在变更的数据库文件。备份副本应有数据库/规则/服务端版本，恢复时先检查相容性。

自动化复用现有规则、资产、UI 回归，增加独立进程服务端/客户端测试和提交点故障注入。公网双机、真断网及发布包体验保留人工验收，禁止以 `127.0.0.1` 同进程测试替代。

### 7.2 发包的硬门槛

1. 会阻止开局/出牌/回家，或造成丢档、丢物、复制物品、账户/房间串数据的缺陷清零。
2. 现有全量回归与新增联网回归通过；仍以退出码与未预期错误日志判断，不只看 PASS 文本。
3. 至少两名真人使用同一发布包，在不同网络完成单人和双人流程；撤离、死亡各有资产对账记录。
4. 对每个持久提交边界完成中断恢复验收，包含“已经提交但成功消息未送达”。
5. 已返回成功的普通操作，服务端进程重启后仍存在；整机/磁盘故障的备份回退限制单独说明。
6. 可重新登录、重新进局、查未查看结算；客户端退出不导致失去恢复入口。
7. 达到验证过的容量基线，无持续增长的异常日志/内存/请求队列；若容量不足，先设上限，不承诺未经测量的在线人数。
8. 建议体验目标：客户端到服务器往返延迟不超过 150ms 的测试条件下，普通操作从提交到确认 P95 不超过 1 秒（不含表现动画）；记录真实测量，解释未达目标的环节。
9. 发布包无调试发物/时间快进入口，启动指引、构建号、更新方式、问题反馈和已知限制完整。

零丢档是发布门槛，不代表任何灾难都有零回退。备份恢复和进程恢复按 §4.3 分开验收。

## 8. 朋友连续试玩期间怎么运行

### 8.1 发包内容

- Windows 游戏包、版本/构建号、更新说明。
- 一页玩家指引：激活、农场操作、创建/加入房间、断线恢复、问题反馈。
- 每位玩家单独的邀请凭据；凭据不写进公共说明、日志或仓库。
- 已知限制：操作需要联网、双人合作、维护安排、线上档与本地档分开。

### 8.2 运行节奏

1. 先由开发者与一名朋友完成两晚的小范围试运行，跨真实日期观察农场和市场；有重大缺陷先停止扩大邀请。
2. 稳定后发给其余朋友，建议连续观察 7～14 天。使用同一批档，不因小更新频繁重置。
3. 检查登录/房间/保存失败、恢复失败、结算异常与运行资源；维护需提前在游戏里提示，避免半局强更。
4. 每次修复写变更说明，包含是否涉及规则、协议、存档迁移与已知风险。
5. 若发现资产一致性问题，先关闭相关操作或新局入口并留存证据；不要直接改数据库数字掩盖问题。

备份方案已确认（2026-10-02）为本地/手动：每日至少下载一次一致备份、保留七天，每次更新前额外备份；备份存放在服务器之外的开发者机器。实际周期、恢复操作与权限在 M4 演练后记录；30 分钟级自动备份列为可选升级。全量回退会影响所有测试者，不能由单人投诉触发自动全服回档。

### 8.3 要收集的玩法证据

| 问题 | 最小记录 |
| --- | --- |
| 能否自己上手 | 首次完成播种、制作、配装、进洞分别需要哪些帮助 |
| 农场等待是否有事可做 | 上线频率、作物等待期间是否会主动下洞、资源短缺点 |
| 双人是否值得合作 | 共同选路、救援、让物资、撤离分歧的实际例子 |
| 经济是否持续 | 制作/补给成本、带回收益、失败后能否低成本再出发 |
| 网络体验是否打断游戏 | 操作确认耗时、重连成功率、卡住的具体界面和错误编号 |
| 第二天是否愿意回来 | 中断原因、最想改的三件事、是否完成下一轮成长 |

反馈可以通过朋友现有聊天工具手工发送，不开发论坛/工单平台。游戏诊断与试玩统计只收本游戏所需内容，不上传电脑里的无关数据或凭据。

## 9. 后补与暂缓范围

**首版稳定后可以考虑：**只读好友农场访问、简单好友列表、房间列表、更多快捷信号、较方便的更新入口、小型管理页面。这些功能不是 M5 发包门槛；增加农场协作种地必须另写权限和并发规则。

3. 公网入口：**已确认不使用域名**，采用 IP＋自签证书，客户端内置证书，TLS 由 Godot 服务端直接提供（§2.1 第 3 条选型）。M0 核实端口占用与安全组放行。
4. 试玩规模：**已确认首批 6～10 人，全部 Windows**；容量目标按 §7.1 T16 验证。
5. 线上档：**已确认新建独立线上档**；现有本地档保留，不自动上传，也不做一次性迁移。
6. Godot 事务存储适配依赖通过验证；数据库提交、快照大小、服务端规则运行和真实延迟可接受。（M0 技术验证项，无需用户决策）
7. 备份：**已确认本地/手动备份**，开发者每日至少下载一次一致备份、每次更新前额外备份，维护/恢复由开发者手工承担；修订见 §4.3 与 §8.2。

工期估算在 M0 后按工作包给出；农场所有按钮改为线上命令，以及跨两人资产事务，是主要工作量。现有玩法复用不能等同于“只加一个连接按钮”。
